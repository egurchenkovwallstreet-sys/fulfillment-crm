**Цель:** автоматизация работы с селлерами Wildberries по модели FBS.

## 3. Роли пользователей и права доступа (жёстко)

### 3.1. Администратор (владелец)
- Полный доступ ко всему.
- Управление селлерами (добавление, редактирование, удаление, токены).
- Управление товарами, ячейками, остатками (включая редактирование).
- Настройка ценовых групп и индивидуальных цен.
- Просмотр всей финансовой информации (выручка, обороты).
- Доступ ко всем отчётам и дашбордам.

### 3.2. Менеджер фулфилмента
**Работает ТОЛЬКО с заказами и складскими операциями.**
- Приёмка товаров (сканирование, ввод количества).
- Смена номеров ячеек (переназначение).
- Формирование листа подбора, сборка, печать этикеток FBS.
- Формирование поставок, печать ШК поставки.
- Сканирование возвратов (через кнопку «Возврат»).
- **НЕ ВИДИТ ЦЕН, СТОИМОСТИ, ВЫРУЧКИ И ЛЮБЫХ ФИНАНСОВЫХ ДАННЫХ.**
- **НЕ РЕДАКТИРУЕТ** селлеров, товары, остатки (кроме списания через сборку).

### 3.3. Селлер (клиент)
- Отдельный личный кабинет с логином/паролем (генерируется системой).
- Видит только свои данные:
  - Остатки товаров (в штуках).
  - Количество заказов за день и за неделю.
  - (В будущем) свою задолженность за обработку.
- **НЕ ВИДИТ ЧУЖИХ ДАННЫХ И ФИНАНСОВ ДРУГИХ СЕЛЛЕРОВ.**
- Может нажать кнопку «Обновить данные» для ручной синхронизации с WB.

## 5. Модуль приёмки товара

### 5.1. Приёмка для существующего товара
1. Сотрудник сканирует баркод товара.
2. Система **автоматически** запрашивает карточку WB (Content API, поле `needKiz`) и показывает, требуется ли «Честный знак».
3. Вводит количество единиц.
4. Система автоматически подставляет номер ячейки (где уже лежит этот баркод).
5. Остатки увеличиваются на введённое количество.
6. Данные синхронизируются с WB (остатки на выбранном складе FBS).

**Склад FBS при приёмке:** менеджер выбирает селлера и точку отгрузки WB (как в сборке FBS).

**Режимы остатков (22.08.2026):**

| Режим | По умолчанию | Действие |
|-------|--------------|----------|
| **Приёмка** | ✅ Да | Фактическое количество → + в CRM → + к остатку в ЛК WB на выбранном складе |
| **Сверка с WB** | Нет | Остаток CRM = остаток ЛК WB; красное подтверждение сверки на фулфилменте |


### 5.2. Приёмка для нового товара (новый баркод)
1. Сотрудник сканирует баркод.
2. Система **автоматически** проверяет карточку WB (`needKiz`) и сохраняет флаг `requires_marking` у товара.
3. Вводит количество.
3. Система видит, что баркод новый.
4. Два варианта:
   - **Автоматически** — система сама назначает свободную ячейку.
   - **Вручную** — менеджер или админ выбирает номер ячейки (для сортировки по размерам/артикулам).
5. Ячейка привязывается к этому баркоду навсегда (для данного селлера).
6. Остатки увеличиваются.
7. Синхронизация с WB.

### 5.3. Правила хранения
- Один баркод = одна ячейка (но в ней может быть много единиц).
- На каждой коробке/ячейке этикетка: название селлера, баркод товара, номер ячейки.
- Этикетки генерируются при **первой приёмке** (новая ячейка) и при **переносе** товара; печать через браузер (**75×120 мм**, книжная ориентация; номер ячейки — 60% высоты).
- Раздел **«Ячейки»** в CRM: список товаров по селлеру, повторная печать и перенос.

## 6. Модуль заказов FBS (синхронизация с WB)

### 6.1. Режимы синхронизации
- **Автоматическая:** каждые 10–20 минут (запрос новых заказов и статусов по API).
- **Ручная:** кнопка «Обновить данные» в кабинете селлера или менеджера (перед финальной сборкой).

### 6.2. Формирование листа подбора (внутренний)
1. Система запрашивает у WB сборочные задания (лист подбора WB).
2. Преобразует их в **свой внутренний лист подбора** с группировкой по ячейкам:

| Ячейка | Баркод | Количество собрать |
|--------|--------|---------------------|
| №1     | 460...  | 5 шт.              |
| №3     | 462...  | 8 шт.              |

3. Лист подбора можно **распечатать в PDF** (A4, книжная ориентация) из кабинета сборки.

**Макет печати** (утверждён 22.08.2026, `docs/pick-list-mockup.html`):
- Шапка 1-го листа: название ИП (обычным шрифтом), дата, общее количество заказов, № листа.
- Таблица: **25 строк на лист**; при большем числе позиций — следующие листы с пометкой «Стр. N из M».
- Колонки: ячейка (14pt **жирный**), кол-во, баркод, название (11pt обычный), квадрат для отметки ручкой.
- Группировка по ячейкам (как в таблице выше) + название товара из карточки склада.

### 6.3. Статусы заказов и счётчики (как во вкладках ЛК Wildberries)

Система синхронизирует статусы через `POST /api/v3/orders/status` и хранит:
- `wb_supplier_status` — статус со стороны продавца (new / confirm / complete / cancel …)
- `wb_status` — статус на стороне WB (waiting / sorted / sold / canceled …)

**Счётчики на дашборде и в кабинете сборки должны совпадать с вкладками ЛК WB:**

| Вкладка в CRM | Условие в API WB |
|---------------|------------------|
| **Новые заказы** | `supplierStatus = new` (число из `GET /api/v3/orders/new`) |
| **На сборке** | `supplierStatus = confirm` |
| **В доставке** | `supplierStatus = complete` **и** `wbStatus = waiting` |

**Не входят в «В доставке»** (исключаются из счётчика):
- `wbStatus = sorted` — уже принят на СЦ WB (в поставке был «Ждёт сортировки» = `waiting`)
- `wbStatus = sold`, `ready_for_pickup`, `defect`
- отмены: `canceled`, `canceled_by_client`, `canceled_by_carrier`, `cancel`, `declined_by_client`

Счётчики на дашборде берутся из **live API** при синке и кэшируются на Seller (`wb_count_*`):

1. **Новые** — число из `GET /api/v3/orders/new` (с фильтром включённых складов).
2. **На сборке / В доставке** — `POST /api/v3/orders/status` по объединённому списку ID:
   - заказы в БД CRM (включённые склады);
   - архив WB за 30 дней (`GET /api/v3/orders`);
   - заказы из поставок, переданных в доставку (`GET /api/v3/supplies`, `done=true` → order-ids).

В поставке WB статус **«Ждёт сортировки»** = `wbStatus = waiting` (не `sorted`).

Ручная и автоматическая синхронизация обновляет счётчики и сохраняет их в карточке селлера для быстрого отображения на дашборде и в **Сборка FBS**.

## 7. Модуль сборки и печати этикеток FBS

### 7.1. Процесс сборки
1. Менеджер открывает **Сборка FBS** → выбирает селлера.
2. На экране селлера — три вкладки стадий (цвета как на дашборде): **Новые** (красный), **На сборке** (оранжевый), **В доставке** (синий). Счётчики вкладок совпадают с ЛК WB.
3. **«На сборку»** / **«Все на сборку»** — поштучно или массово: создаётся поставка WB, заказ добавляется, статус → `confirm`.
4. **«В доставку»** — передача поставки WB в доставку (`PATCH .../deliver`), статус → `complete` + `waiting`.
5. Кнопка **«Лист подбора»** / **«Начать сборку»** — формирует лист подбора и запрашивает стикеры WB для новых заказов.
6. Сотрудник идёт с листом подбора по ячейкам.

### 7.2. Печать этикетки FBS
1. Сотрудник сканирует баркод конкретного заказа (на товаре или упаковке).
2. Система сравнивает с листом подбора.
   - **Если баркода нет в листе** → звуковой сигнал + красное табло (ошибка).
   - **Если есть и товар без ЧЗ**:
     - Этикетка FBS сразу отправляется на печать (стикер уже загружен при «Начать сборку»).
   - **Если есть и товар с ЧЗ** (`requires_marking`):
     - Стикер **не печатается** до привязки ЧЗ.
     - Система просит отсканировать DataMatrix с упаковки.
     - Код привязывается к заказу в WB через API (`sgtin`).
     - **Только после успешной привязки** — автоматическая печать стикера.
     - При ошибке — понятное сообщение; доступна **«Заменить товар»** (сброс заказа).

### 7.3. Требование по скорости
- От сканирования до печати — **менее 2 секунд**. Сотрудник не должен ждать.

### 7.4. Форматы и способ печати (зафиксировано 22.08.2026, обновлено 22.08.2026)

**Сборка FBS (стикеры, < 2 сек):** локальный **брендированный агент `.exe`** на ПК склада (Windows) — `docs/print-agent.md`. CRM шлёт PNG на `http://127.0.0.1:9123/print` без диалога Chrome.

**Лист подбора, этикетки ячеек:** печать через **Google Chrome** (`window.print()`), принтер Xprinter 365/370 в системе Windows.

| Документ | Формат | Ориентация |
|----------|--------|------------|
| Лист подбора | **A4** | книжная |
| Этикетка ячейки | **75×120 мм** | книжная |
| Стикер FBS (заказ) | **58×40 мм** | — |
| QR/ШК поставки | **58×40 мм** | — |

**Без служебных надписей Chrome:** дата, URL (`about:blank`), заголовок вкладки, номер страницы. В CSS: `@page { margin: 0; size: … }`, пустой `<title>`. В диалоге печати Chrome при необходимости снять «Колонтитулы».

## 8. Модуль Честного знака (маркировка)

### 8.1. Обязательная привязка
- Для товаров с обязательной маркировкой привязка кода DataMatrix (КИЗ) к этикетке FBS — **обязательна**.
- **Без этой привязки товар НЕ МОЖЕТ БЫТЬ ОТПРАВЛЕН**.
- Система блокирует передачу статуса в WB, пока код не отсканирован и не привязан.

### 8.2. Процесс привязки
1. После скана баркода заказа (товар с `requires_marking`) сотрудник сканирует код DataMatrix с упаковки товара.
2. Система привязывает его к этому заказу в кабинете WB через API (`PUT /api/v3/orders/{id}/meta/sgtin`).
3. **Сразу после привязки** CRM опрашивает статус проверки в WB (`POST /api/marketplace/v3/orders/meta`) и продолжает опрос каждые 5–10 сек, пока WB не вернёт финальный результат.
4. **Только после успешной проверки** (`filled`, `sgtinIntroduced`, `sgtinSoldB2B` и др.) — автоматическая печать стикера FBS и `marking_bound = true`.
5. Пока статус `pending` — в таблице заказов индикатор ожидания; кнопка «В доставку» заблокирована.
6. При ошибке проверки (`required`, `sgtinNotFound`, `sgtinInvalidFormat`, `sgtinEmitted` и др.) — **красное модальное окно** с данными заказа и текстом ошибки; кнопка **«Заменить товар»**.
7. Статус привязки отображается в системе: `marking_verify_status` (`pending` / `verified` / `error`), `marking_bound` — только после `verified`.
8. При ошибке привязки PUT — понятное сообщение; кнопка **«Заменить товар»** сбрасывает заказ для другого экземпляра.

### 8.3. Блокировка доставки
- Передача в доставку (`PATCH .../deliver`) **заблокирована**, пока для маркированного заказа `marking_verify_status !== verified`.
- CRM не устанавливает `marking_bound = true` сразу после PUT — только после подтверждения WB.

## 9. Модуль формирования поставок

> **Статус (24.08.2026):** ✅ Полный цикл в одном окне «Сборка FBS»: лист подбора → скан → стикер → ЧЗ → передача в доставку (QR поставки). Блокировка шагов и модальные подтверждения.

### 9.1. Условия формирования
- Поставка формируется ТОЛЬКО после того, как ВСЕ заказы в ней:
  - Собраны.
  - Упакованы.
  - Оклеены этикетками FBS.
  - (Для маркированных) привязаны коды Честного знака.

### 9.2. Печать ШК поставки
- Доступна только после выполнения всех условий выше.
- Система запрашивает через API WB штрихкод поставки.
- **Тип кода:** общий QR-код для сортировочного центра (без грузомест, просто штора поставки).
- Печать осуществляется ТОЛЬКО из CRM.
- ШК клеится на видимое место на поставке.

## 10. Модуль списания остатков

- После того как поставка сформирована и ШК распечатан, система **автоматически** списывает собранные товары с остатков склада (ячеек).
- Списание происходит только для товаров, которые реально переданы в WB (статус поставки подтверждён).

## 11. Модуль возвратов

### 11.1. Кнопка «Возврат»
- Отдельная кнопка в интерфейсе менеджера.
- Принцип работы идентичен приёмке, но:
  - Сканируется баркод товара.
  - Вводится количество.
  - Система добавляет товар обратно на остаток в ту же ячейку.
- Возврат помечается отдельным флагом/файлом, чтобы селлер и админ видели, что это возврат, а не новая поставка.

## 12. Модуль ценообразования и финансов

### 12.1. Ценовые группы (габаритные)
- Администратор создаёт 4–5 групп (например: малогабаритный, средний, крупный, негабарит, сверхнегабарит).
- Для каждой группы задаётся стоимость обработки за 1 единицу.

### 12.2. Привязка товара к группе
- При добавлении товара (или редактировании) администратор выбирает группу → цена подставляется автоматически.
- Если цена не задана — стоимость не отображается.

### 12.3. Индивидуальная цена (ручной ввод)
- В карточке товара есть поле «Индивидуальная стоимость».
- Если оно заполнено — приоритет выше групповой цены.
- Администратор может найти товар:
  - по баркоду
  - по номеру ячейки
- И вручную изменить цену для этого конкретного товара.

### 12.3.1. Назначение тарифа селлеру (реализовано в CRM UI)
- Раздел **«Селлеры»** → кнопка **«Тариф»** у каждого селлера.
- Два режима:
  - **На все товары** — единый тариф (₽/шт.) на все SKU селлера (`individual_price`).
  - **На ценовую группу** — тариф только для товаров выбранной группы; опционально назначить группу товарам без группы.
- Ценовые группы создаются в Django-admin («Ценовые группы»).

### 12.4. Финансовая аналитика (только админ)
- По каждому селлеру: количество отгруженных заказов × тариф = сумма за обработку.
- **Источник отгрузок:** поставки WB `done=true`, заказы из WB API (`order-ids`), в т.ч. отгруженные **до/вне CRM**.
- Фильтр: только включённые FBS-склады селлера (`SellerWarehouse.is_enabled`).
- **Кабинет селлера:** график отгрузок за 4 недели — заказы и суммы по дням.
- **Админ `/billing`:** объединённая статистика всех селлеров + таблица по каждому.
- В планах: отчёты за день/месяц/всё время, задолженность селлера.

## 13. Дашборды и отчёты

### 13.1. Дашборд администратора / менеджера (главный экран)
- **Новые заказы** — красная карточка, статус «Новый» в WB.
- **На сборке** — оранжевая карточка, статус «На сборке» в WB.
- **В доставке** — синяя карточка, `complete + waiting` (см. §6.3). **Проверено:** совпадает с вкладкой «В доставке» в ЛК WB.
- **Селлеров** — число подключённых к API (только admin).
- **Остатков (SKU)** — по ячейкам склада.
- Кнопка **«Обновить данные WB»** — ручная синхронизация заказов и статусов.
- Автообновление: Celery каждые 15 минут.

### 13.2. Дашборд внутри селлера (для админа)
- Детализация по конкретному селлеру:
  - Остатки по каждому товару.
  - Заказы за день/неделю.
  - Выручка за день/неделю/месяц/всё время (на основе стоимости обработки).
  - Возможность просматривать и редактировать цены/группы.
- **Реализовано:** раздел **«Статистика»** (`/billing`) — сводка по **всем** селлерам: график отгрузок (4 недели, заказы + ₽), таблица по селлерам за выбранную неделю. Тарифы — в разделе «Селлеры».

### 13.3. Кабинет селлера
- Видит только свои остатки и свои заказы.
- **Заказы за день / неделю / месяц** — календарные периоды (МСК), источник: **WB Statistics API** (`GET /api/v1/supplier/orders`), уникальные заказы по `srid`, только FBS (`warehouseType` = «Склад продавца»). Должно совпадать со сводным отчётом WB («Количество заказов»). Токен WB с категорией «Статистика».
- Сравнение с предыдущим периодом (стрелка и %): вчера / прошлая неделя / прошлый месяц.
- **Стадии WB:** Новые / На сборке / В доставке — как в разделе «Сборка FBS» (Marketplace API).
- **Отгрузки на склад WB:** заказы из поставок `done=true` по дате `scanDt`/`closedAt`; график по дням за **последние 4 календарные недели** с переключением; **сумма в ₽** по тарифу обработки. Учитываются все заказы из WB, в т.ч. отгруженные вне CRM.
- Таблица товаров: остаток на фулфилменте, заказы д/н/м по штрихкоду, средние продажи (7 дн.), прогноз «хватит на N дней», статус запаса (Догрузить / Норма / Много).
- Детализация по штрихкоду: график заказов за 7 дней.
- В будущем — видит свою сумму задолженности.

### 13.4. Ежедневные отчёты (автоматические)
- Отчёт по количеству заказов за день.
- Отчёт по товарным остаткам.
- Формируются автоматически (например, в конце дня).

## 15. Интеграция с API Wildberries (FBS)

Обязательные вызовы:
- Получение списка новых заказов (`GET /api/v3/orders/new`). ✅
- Получение архива заказов (`GET /api/v3/orders`, до 30 дней). ✅
- Получение статусов заказов (`POST /api/v3/orders/status`). ✅
- Получение этикетки FBS для заказа (`POST /api/v3/orders/stickers`). ✅
- Привязка кода Честного знака к заказу (`PUT .../meta/sgtin`). ✅
- Создание поставки (`POST /api/v3/supplies`). ✅
- Добавление заказов в поставку (`PATCH .../supplies/{id}/orders`). ✅
- Передача поставки в доставку (`PATCH .../supplies/{id}/deliver`). ✅
- Получение ШК поставки (`GET .../supplies/{id}/barcode`). ✅
- Список поставок и ID заказов в поставке (`GET /api/v3/supplies`, `GET .../order-ids`). ✅
- Получение сборочных заданий (лист подбора). ✅ (внутренний лист по ячейкам)
- **Статистика заказов (сводный отчёт):** `GET /api/v1/supplier/orders` на `statistics-api.wildberries.ru`. ✅ (кабинет селлера)
- Обновление остатков FBS (`PUT/POST /api/v3/stocks/{warehouseId}`). ✅ приёмка
- Отправка статуса готовности заказа. 🟡 (через deliver поставки)

**Все вызовы — через API-токен селлера.**

## 16. Примечания и допущения

- Честный знак — обязателен для маркированных товаров.
- Товар без привязки Честного знака не отправляется.
- Менеджер не видит финансов ни при каких условиях.
- Селлер получает доступ только к своим данным.
- Система должна работать с двумя моделями принтеров Xprinter (365 и 370).
- Выбор стека и БД — на усмотрение разработчика.
- В будущем: возможна привязка стоимости обработки и отображение суммы в кабинете селлера.
